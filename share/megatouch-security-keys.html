Findings

the four starting assumptions, checked
"The first 6 digits tie a key to a version"
Corrected No version checks the SA digits.

A key is accepted when the software can open it with one of its password sets, decrypt it with its cipher, and find its 8-byte signature. A different part number only makes the game wipe NVRAM ("Dallas Key mismatch, re-initing NVRAM"). Several SA numbers work on one version because Merit issued several part numbers with identical contents. Emulator test: Diamond, Emerald and Jade keys relabelled with the made-up part number SA999901 all boot normally. The same rule covers the DS1991-era Force and ION keys, which use their Maxx cousin's cipher; on the 2007-and-later keys the gate is the signature at 0x0F5 plus a checksum (part-number edits there were not boot-tested).

"The last two digits are the territory"
Confirmed Same numbering in every generation.

01 USA-STD, 05 PORTUGAL and 33 CAN-VER2 mean the same thing on XL, MAXX, Crown, Force and ION keys (every Force key and ION up to 2010 is 01; ION 2011–2013 use 09 USA-VER1). The key also stores the territory name and, from Sapphire on, a country code.

"Merit locked features on the key"
Confirmed 80 two-bit option slots on every key up to 2006, 120 from 2007.

Each slot is locked off, locked on, or operator-selectable. TournaMAXX is slot 0x14: forced on in the Jade keys, locked off in both Crown keys. The XL and DOS MAXX keys carry the same table; Sapphire keys have 88 slots. On Force and ION keys TournaMAXX is never locked off, and from 2007 the key also chooses the product variant: Touch2Play, KidZpace, MindSpark, UAE prize and lease mode are key-only switches, off on every standard key.

"Menus only accept serials in a range"
Confirmed Linux builds 2002–2006, Force included; dropped in 2007.

Ruby 2 through Crown check the button's factory serial against the lots Merit bought. A failure shuts the game down at boot with "KEY RANGE MISMATCH". keyflasher can rewrite contents but not that serial. Force 2003.5 and 2005 / 2005.5 run the very same programs, so the same ranges apply; the 2007-and-later Force and ION software has no range check, only a button-type rule.

Products

Maxx / XL, Force and ION on one code base

Merit sold three lines that all use these keys: XL / MAXX (1997–2005), Force (2002–2011, its own cabinet and motherboard) and ION (2006–2014), plus Touch2Play and Firefly on the ION software. They are not separate systems: Force and ION run the Maxx software of the same year and the key decides which product the machine becomes.

  • The key picks the product. DS1991-era Force and ION keys enable the Force-only game 0x44 (Bowling), which the shared software checks against the motherboard. DS1991 MultiKey 256 bytes, then a 1 KB block from 2007

From 2007: one plain memory block

Force 2007 and ION 2007 onward use a DS1995 (2 KB) or DS1996 (8 KB) memory button: no compartments, no passwords, one 1024-byte block behind a six-byte keystream keyed by the serial and a per-year constant, closed by a 16-bit checksum. It holds the part number, a Unix timestamp, territory text and country code, the MegaNet server and web-portal addresses, the signature, six coin channels, a price byte for each of 300 games, 120 option bytes and a 300-bit game list (field map under "The 2007 key format").

Paired versions such as XL Gold and MAXX 2K share cipher and signature but use different password constants, so their keys are not interchangeable on the same cabinet. Some constants are literally x86 instruction bytes: Diamond's 83 F8 01 76 22 56 8B F0 disassembles to cmp eax,1; jbe ….

Force and ION reuse the Maxx cipher of their year but carry their own password recipe, so on the DS1991-era hardware a Force key cannot be read as a Maxx key — except Force 2003, whose recipe and signature are Ruby 2's. The password generators reproduce the passwords stored in 48 of the 49 dumps across both lines.

Cabinet binding

why most builds carry two password sets

DOS: XL cabinet or MAXX cabinet

Every DOS build from XL Gold on runs on both cabinet types, chosen by the boot scripts' environment variables. The key family has to match the cabinet.

  • XLSYSTYPE=MAXX selects the MAXX password set (Platinum → Emerald builds). Titanium also switches to the Emerald signature, so Titanium on a MAXX cabinet wants an Emerald key.
  • XLNEWIO=YES (new I/O board) does the same for XL Gold and MAXX 2K.
  • XLKEYFILE=<file> loads the key from a file, a development feature. XLDEVSYS=YES marks a development system.

Linux: MAXX or FORCE

Ruby 2 and Jade 2 ship the same start binary as Force 2003.5 and 2005.5. The product is decided at boot.

  • The "MegaTouch FORCE" banner and Force mode need the Intel 810 board (type 4) with the USB I/O board.
  • The key must enable game 0x44 (Bowling, marked Force-only in the game table) exactly when it runs on Force hardware, or the signature check fails. Both Crown keys examined are MAXX keys.
  • Allowed boards: Intel 430TX + ATI Rage, Intel 430VX + S3 Trio64, VIA VT8501 + VT82C686, Intel 810 + CMI8738. Anything else stops with "INVALID MOTHERBOARD DETECTED".

The Crown CAN-VER2 key in the dump set is on a family-0x02 button, so a stock Crown build would shut it down at boot even though it decrypts correctly. It was probably re-flashed onto a DS1991 blank, or ran on a patched build.

The check is guarded by an anti-debug trap: if a breakpoint byte (INT3) is found inside it, the game loops forever printing "Not Jersey Key, Not Dallas Key, must be Florida Key". At runtime the game re-reads the serial and shuts down after ten mismatches ("SECURITY KEY MISMATCH").

The Force cabinets enforce the Maxx windows

Force ran the same software as the Maxx of the same year, so it enforces the same ranges. That was settled by comparing the packed start launchers byte for byte: Force 2003.5 v11.00 is identical to Maxx Ruby 2 V11.00, Force 2005 v14.00 to Maxx Jade V14.00, and Force 2005.5 v15.10 to Maxx Jade 2 V15.10. The other Force builds (2003 v10.09, 2004, 2006 and ION 2006) have no matching binary in the collection, so they are taken to follow their nearest Maxx sibling.

The 2007-and-later keys have no window at all — the cipher is keyed from the button's serial, so a key simply decrypts to garbage on the wrong button and fails its own checksum. What those releases do constrain is the button type: it must be a DS1995 or DS1996, and large enough for the release's block offset. ION 2013 writes its block at 7 KB, so only a DS1996 will do.

What each slot does, and which releases offer it

Merit's own operator help text survives inside the later programs as <b>Label</b>|text strings. It covers 67 of the 120 slots, so for those the description is Merit's wording rather than an inference; the other 53 are described from the code that reads them. Five slots (0x0C, 0x0F, 0x2F, 0x43, 0x47) meant something different in the Crown era than the name Merit later gave them, so both readings are recorded and the Crown-era one is shown for Crown-era keys.

How the slots changed across releases

  • Sapphire adds the MegaNet services (MegaWeb, Prize Zone, E-Channel, Hot Topics, premium content).
  • Jade adds pay-per-time, lease mode, demo mode and the scrolling marquee as key-only switches, plus Operator Web, ShowTenders, Fantasy Sports and card-back ads as operator settings.
  • Jade 2 adds senior play and the switch that hides the TournaMAXX ranking screens.
  • Ruby 2 and Sapphire had a "six-star access" group (high scores, bookkeeping, volume, calibration, TournaMAXX update from the operator shortcut) that Jade dropped; Ruby 2 also had "Golf has women".
  • TournaMAXX (slot 0x14) is a key-only switch in every build from Ruby 2 to Crown. On ION it became a menu toggle ("Select Tournament Mode"), still usable only when the key leaves it selectable.

DOS builds: settings

The DOS operator menus live in SETUP.DLL, which reaches NVRAM through MEGACDLL's exported _NVRAMDATA. Each import fixup carries the NVRAM offset, so every menu access is located exactly. Every credit counter is a current/lifetime pair, and coin books are six float channels. MAXX 3.06 has no text labels and is mapped as "2K minus 0x30". XL 6000 and XL Gold have no disk image here; their game code touches the same offsets as 3.06 and 2K respectively.

Per-game books and game names

Game IDs are the record order of the game table, GAMEDATA.DAT on DOS and gamedata.dat on Linux: 51 games on MAXX 3.06, 84 on Emerald, 146 on Sapphire, 195 on Crown. DOS keeps one record per game ID with its menu flags, price, current and lifetime credits, loader setting, shortest/average/longest play time and games by number of players. The setup program's clear-books loops run exactly to the game count, which ties the index to the game table. Real data from the Emerald 2 played image:

Crown crypto

not supported by keyflasher; recovered

Same structure as Jade (increment 0x16) with new seeds 12 78 37 F3 and a new serial-to-laserMath formula, where k is the 8-byte ROM ID with the family byte first:

lm0 = ((k3 - k4) - k5) ^ k1 ^ 0x7F lm1 = (((k1 + k2) - k3) - k4) ^ 0xF3 lm2 = (k4 + 0xBC) ^ (2·k2 + k1) lm3 = 2·k4 + k5 + k1 + 0x7F

It decrypts the USA-STD Crown key to the known plaintext with zero differing bytes. On Linux cabinets the host computes the DS1991 passwords and the I/O board's EZ-USB firmware reads the key and returns it masked with a 4-byte value. Nicholas Navaroli's keyless patch replays that USB traffic, which is why it never needed the cipher.

The Force / ION line

2002–2014

Force and ION are not separate systems. They are the same software as the Maxx of the same year, and the key decides which product the machine becomes — Maxx Ruby 2 V11.00 and Force 2003.5 share a game binary, as do Jade 2 V15.10 and Force 2005.5. Through 2006 the Force and ION keys reuse their Maxx cousin's cipher byte for byte; only the signature and the password constants differ. Force 2003 even uses the same passwords as Maxx Ruby 2.

This also settles an old question. The Crown key gate accepts two signature values, and the second (ending 87) was suspected to be the Force one. It is not: Force 2005 carries exactly the same signature as Maxx Jade, and the Force/Maxx difference lands on the first byte instead — Force 2006 reads 86 24… where Crown reads 87 23…. That is the cabinet-platform modifier seen from the key side for the first time. The 87-ending variant belongs to a different rule, about high-bit characters in the territory name.

A game number only means something next to its release

A key stores games by number, and the number is nothing more than a position in that release's game table — GAMEDATA.DAT on DOS, gamedata.dat on Linux, a compiled enum from 2007 on. The same number is therefore a different game on a different release, so naming a key's games means using its own software's table. Twenty-four release tables were recovered, plus the two compiled into the Force and ION programs.

  • Ruby, Ruby 2 and Force 2003 keep /usr/local/share/merit on partition 7, so their table lives at /config/gamedata.dat there.
  • Force 2006 ships a stale table: the only image's file is entry-for-entry Force 2003's 102 games, while the Force 2006 key prices Crown-era numbers up to 0xC1. Force 2006 and ION 2006 are read with Crown's 195-entry table instead.
  • The Force numbering agrees with the ION enum on all 168 numbers that could be pinned, so the ION names fill the Force gaps.

Verification: every Force/ION DS1991-era dump decrypts byte-exact and re-encrypts byte-exact, and the password generators reproduce the passwords stored in 48 of 49 dumps across the whole collection.

Force and ION games

Force game tables start smaller than their Maxx siblings (Force 2003: 102 games, Force 2004: 146) and then match the Maxx software they share (Force 2005 / 2005.5: 173 / 180). The 2007-and-later keys have room for 300 games and keep the Maxx numbering — 0 is still Solitaire, 4 Match 'Em Up, and a retired game keeps its number (g_match_removed). Genuine keys enable 137 (Force 2009) to 200 (ION 2014) games; the 2007 keys, which predate the on/off list, enable a game by giving it a price. The only Force 2006 image carries a stale copy of Force 2003's table, so Force 2006 and ION 2006 keys are named from Crown's.

Settings memory. Up to 2006 Force keeps the same nvram.dat as the Maxx software it shares. From 2007 the settings moved to XML (/merit/settings.xml) and SQLite, and nvram.dat shrank to 5,792 bytes — not mapped yet.

The 2007 key format

Force 2007+, ION 2007+

In 2007 Merit abandoned the DS1991 MultiKey. From Force 2007 and ION 2007 the key is an ordinary memory iButton — a DS1995 (2 KB) or DS1996 (8 KB) — with no protected compartments and no passwords at all. The entire key is one 1024-byte block in plain memory, and only a weak keystream stands in front of it.

That keystream is a repeating six-byte pattern built from the button's serial and a per-year constant. Since the plaintext always begins with the part number SAnnnn, six known characters hand over the whole pattern, and long runs of blank data print it outright. Running the derivation backwards even recovers the button's serial number — which is how two unlabelled dumps in the collection were identified, one as a Force 2011 key and one as an ION 2014 key read over USB.

The layout was read straight out of the game software: KeyManager::Read copies the decrypted block into its own object at offset zero, so every field offset in the code is a key offset.

The key editor

Megatouch Key Tool

Everything on this page is built into one program that opens, edits and generates keys for all 33 releases from XL R1 to ION 2014 (a single Windows .exe, or Python source). It shows every option with a plain name and a description, in Merit's own operator help text for 67 of the 120 slots, grouped by who sets it: the operator menus, or the key alone. Games carry the names from that release's own game table. When the button serial is changed it checks the 1-Wire checksum, the button family and the serial window the release enforces, and can suggest a serial the release accepts. Every save is re-decrypted to verify it.

Its regression suite loads all 107 dumps in the collection, round-trips every one, generates a key for each of the 33 releases, and asserts the layout, name and serial rules above.

Open items

what is still unknown
  • A genuine ION 2014 key dump. The only sample contradicts itself — country code 1 (Canada) with territory text USA-STD, and a date that decodes to 1977 — so it is almost certainly hand-made.
  • The serial-tied bytes at offset 0x012 and the three copies at 0x3F0 on Gen 4 keys. Six otherwise byte-identical ION 2009 keys differ in nothing else, and the game never reads 0x3F0 — most likely the programmer's own anti-clone marker.
  • Game names for 8 ION slots. The Force-line gaps are filled from ION, which agrees on all 168 Force ids that could be pinned.
  • The 2007-and-later settings memory, which moved to XML files plus SQLite, so none of the earlier NVRAM mapping carries over.
  • The executable self-read inside the Gen 4 key check — found, not analysed.
  • Which options the DOS operator menus offer. The DOS keys carry the same 80-slot table, but the DOS menus reach most slots through an index table that has not been traced, so about 20 are confirmed as menu settings. Also the credit-book rows in the Linux amusement.db (an obsolete SQLite 2 file).
  • The Force 2007–2011 operator menus, not among the extracted files; those keys' options are classified from ION 2011's menus.
  • Why a Jade-labelled key carries the Force platform bit. Two keys with the same part number SA3079 differ in it, so it is a per-key choice rather than a property of the part number.
  • MegaNet server-side serial checks remain out of scope — they run on Merit's servers.
